# Mosaic: What Building Evals Taught Me About Trusting My Own Fixes

One of the more humbling problems I've worked through in Mosaic is the screenshot autofill feature — you upload a screenshot of an event card from Instagram or TikTok, and the app tries to pull out a title, date, time, location, category, and description automatically, using OCR text and a set of deterministic heuristics rather than a network call. It's a small feature on paper. In practice it's been the single best teacher I've had on this project about the difference between a fix that looks done and a fix that's actually done.

Like any product problem, this one started concrete, not abstract: real screenshots that real cards produced wrong results on. A card for a "Non Visual Drawing Club" event came back with a garbled title, a blank location, and a date pulled from the wrong part of the image. A "Summer Reading Closing Festival: Bookbinding" card fared worse — the title guess was a fragment of an attribution overlay, not the event name at all. The instinct in the moment is to just fix each one and move on. What I did instead was start a running file, `EVALS.md`, where every real failure gets logged as a row: what the screenshot actually showed, what the fields should have said, what they actually said, and exactly which parts were wrong. Real case in, expected output stated plainly, actual output checked against it — that loop, repeated, is the whole discipline.

The heuristics themselves ended up being genuinely interesting problems once I had real failures to design against instead of guessing what OCR noise looks like. Titles get picked by finding the tallest cluster of text on the image, since flyers and event cards almost always render the headline biggest — but that only works once you've filtered out the noise that's often just as visually prominent: UI chrome, attribution lines like "From @someone," date/time headers, and OCR fragments so garbled they're just a stray bracket next to one real letter. Locations started out only recognizing street addresses, which meant any card that just named a venue — a library, a park, a museum — came back blank, so I added a fallback that recognizes venue words directly, deliberately leaving out ambiguous ones like "club" or "school" once I found a card whose event name itself contained one and got misread as its own venue.

Here's the part I think is actually worth being honest about, because it happened during this same project and it's exactly the failure mode evals exist to catch. I fixed both of the cases above, wrote unit tests, watched them pass, and updated the eval rows to reflect the fix — except the tests were checking my own hand-typed simulation of what I assumed the real OCR output looked like, not the actual output of running the real screenshot through the real pipeline, because the image file itself wasn't accessible to me at the time. It felt done. The demo got rebuilt and redeployed on the strength of that. Then the actual screenshot got tested again for real, and the title guess came back completely wrong in a new way — a jumble of a "Register" button fragment and an "In Person" badge, because the real image had a busy video background and overlapping UI elements my hand-typed test never modeled, because I'd never actually seen what Tesseract does to that specific image.

That's the trap: a test I wrote myself, based on my own assumptions about the input, will only ever validate my assumptions — it can't catch the gap between what I imagine noisy OCR output looks like and what it actually is. The eval only does its job once it's anchored to the real artifact, not a stand-in for it. I've since made getting the actual file non-negotiable before marking anything in `EVALS.md` as fixed, even when that means asking for it a second time.

The AI-assisted part of this build made writing and rewriting these heuristics fast — a new filter, a new fallback, a new regression test, all cheap to produce. What it didn't do, and what I don't think any tool does for you, is decide when a result is trustworthy enough to call finished. That judgment still has to come from insisting the eval touches reality, not from how confidently a fix reads in the moment it's made.
